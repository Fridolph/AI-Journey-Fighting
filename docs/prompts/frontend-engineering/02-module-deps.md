# 模块依赖图

> **类型**: 前端工程 &nbsp;|&nbsp; **标签**: `依赖分析` `循环依赖` `拓扑图` `SVG`

## 提示词

```md
分析项目内部源码模块的引用关系，生成模块依赖拓扑图。

## 分析规则
- 扫描所有源文件中的内部导入语句（基于 tsconfig paths 别名）
- 下钻到子模块粒度（取别名后两级路径），合并无出度的叶子节点
- 节点数控制在 10~20，每个节点标注模块名 + 一句话职责
- 构建邻接表，DFS 检测双向边和最小环，标注循环引用计数
- 循环依赖用红色加粗虚线高亮，底部附上统计概要和循环对详情

## 输出
- ./docs/module-deps.svg
```

## 适用场景

- **重构前摸底**：改一个模块，看会波及哪些上下游
- **循环依赖治理**：新人容易写出 A→B→A 的死循环，图一跑就知道了
- **模块拆分决策**：当某个模块引用数爆炸，该不该拆，往哪个方向拆
- **Code Review 辅助**：新 PR 引入的依赖关系是否健康

## 最佳实践

1. **先扫全量，再看增量**：第一次对整个项目跑，后续只对改动的模块跑增量分析
2. **循环依赖是红线**：出现红色加粗虚线应立即修复，不修复至少记录到技术债清单
3. **节点数封顶 20**：超出时合并叶子节点，否则图会乱到看不清
4. **结合数据模型图一起看**：依赖图告诉你谁引用了谁，数据模型图告诉你传了什么数据
5. **定期运行**：建议合并到 CI 流程，每个 PR 自动检测是否新增循环依赖
