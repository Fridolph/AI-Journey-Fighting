## 二、为什么有了 Milvus 还要 ES

### 2.1 核心区分：语义检索 vs 词条检索

ES 和 Milvus 不是在争同一个位置，而是解决**两类根本不同的问题**：

| | Milvus（语义检索） | ES（词条检索） |
|--|-------------------|----------------|
| 匹配逻辑 | 「意思差不多」 | 「字面差不多」 |
| 适合输入 | 自然语言问句、模糊概念 | 术语、编号、代码、人名、地名 |
| 典型成功 | 搜「杭州旅游」命中「西湖攻略」 | 搜 `errorCode=5001` 只会命中 5001 |
| 典型失败 | 搜 `i7-13700K` 可能漂到 `i7-12700K` | 搜「西湖攻略」搜不到「杭州旅游」 |

> ⚠️ **注意**：ES 不是「精确搜索」（`=`），而是 **「词条/关键词检索」**。ES 的 `match` 查询仍然是分词后匹配，只是匹配的单位是**词**而不是语义向量。真正的精确匹配（==）在 ES 里是 `term` 查询（针对 `keyword` 类型字段）。

### 2.2 你举的例子非常到位

> 「X-XXXXA 和 X-XXXXB，看结构、类型、型号差不多，LLM 可能认为是一个，但从准确性来说完全就不是」

这正是 ES 的杀手场景——**语义相近但字面不同**的反面：**字面不同但语义相近的归 Milvus，字面相近但实际不同的必须走 ES**。

### 2.3 解决方案：混合检索

**ES 做词条匹配 + Milvus 做语义检索**，两路结果合并去重 → Rerank → LLM 作答。

## 三、倒排索引 vs 正向索引

### 3.1 MySQL：正向索引

```
文档 → 关键词

| id | content |
|----|---------|
| 1  | 今天早上跑步   |
| 2  | 今天晚上跑步   |
| 3  | 今天早上骑车   |
```

搜"跑步" → 遍历每一行 → 匹配 `content` 字段 → 找到 id=1, id=2。数据量越大越慢。

### 3.2 ES：倒排索引

```
关键词 → 文档

"今天" → [1, 2, 3]
"早上" → [1, 3]
"跑步" → [1, 2]
"骑车" → [3]
"晚上" → [2]
```

搜"跑步" → 直接查关键词表 → 定位 [1, 2] → 不需要遍历。**O(1) 找关键词，再按 BM25 排序。**

### 3.3 你的直觉是对的，再补一个更直观的比喻

#### 正向索引 = 图书馆的书架目录

```
你想找「包含"跑步"的书」：
  → 从第 1 排书架开始
  → 抽出第 1 本书，翻一遍，有没有"跑步"？有，记下
  → 抽出第 2 本书，翻一遍，有没有"跑步"？没有，跳过
  → ... 翻完 10000 本书，得到结果
```

这就是你说的「走很多步」——**数据量越大越慢，因为每本书都要翻**。MySQL 的 `LIKE '%跑步%'` 就是这个逻辑。

#### 倒排索引 = 书店后面的索引卡片柜

```
你想找「包含"跑步"的书」：
  → 拉开标着"跑"的抽屉
  → 找到卡片"跑步" → 上面写着：[书1, 书2, 书7, 书99]
  → 直接去拿这 4 本书
```

**不需要翻任何一本不相关的书。** O(1) 找到关键词，然后直接拿到文档 ID 列表，最后按 BM25 排序。

### 3.4 一句话总结

```
正向索引：文档 → 关键词    （MySQL，存记录，遍历查）
倒排索引：关键词 → 文档    （ES，建词典，直接定位）
```

**理解了倒排索引，就理解了 ES。**

## 四、IK 中文分词器

ES 默认分词器不支持中文——"今天早上跑步"会被拆成 `今|天|早|上|跑|步`。IK 分词器专为中文设计，有两种模式：

### 4.1 ik_max_word：索引时用（最细粒度）

```
"今天早上跑步"
→ 今天 | 早上 | 跑步 | 今天早上
```

尽量多切，提高**召回率**（搜索"早上跑步"和"今天运动"都能命中）。

### 4.2 ik_smart：搜索时用（最粗粒度）

```
"今天早上跑步"
→ 今天早上 | 跑步
```

尽量少切，提高**精确率**（不会把无关文档也搜出来）。

```js
// 创建索引时指定
mappings: {
  properties: {
    note_title: {
      type: 'text',
      analyzer: 'ik_max_word',       // 写入时最细粒度切分
      search_analyzer: 'ik_smart'    // 搜索时粗粒度切分
    }
  }
}
```

| 模式 | 时机 | 效果 |
|------|------|------|
| `ik_max_word` | 索引（写入） | 多切，召回率高 |
| `ik_smart` | 搜索（读取） | 少切，精确率高 |

---

### 4.3 安装 IK 分词器：为什么需要一个自定义 Dockerfile

ES 默认不包含 IK 分词器。要在容器里装插件，需要自定义 Dockerfile：

```dockerfile
# elasticsearch/Dockerfile
FROM elasticsearch:8.17.0
RUN elasticsearch-plugin install --batch \
  https://release.infinilabs.com/analysis-ik/elasticsearch-analysis-ik-8.17.0.zip
```

然后 `docker-compose.yml` 里不再用 `image: elasticsearch:8.17.0`，而是：

```yaml
es:
  build: ./elasticsearch   # ← 从本地 Dockerfile 构建（自带 IK）
```

**版本必须严格一致**——IK 插件版本要和 ES 版本完全一致，否则无法加载。

### 4.4 三种分词器实测对比

在 Kibana 里跑 `POST /_analyze`，输入 `"Elasticsearch RAG混合检索知识库"`：

| 分词器 | 输出 | 特点 |
|--------|------|------|
| `standard` | `elasticsearch` `rag` `混` `合` `检` `索` `知` `识` `库` | 英文按空格，**中文逐字拆**——索什么引 |
| `ik_max_word` | `elasticsearch` `rag` `混合` `检索` `知识` `知识库` `库` | **最细粒度**，穷举所有可能，用知识库也能搜到知识 |
| `ik_smart` | `elasticsearch` `rag` `混合` `检索` `知识库` | **最粗粒度**，按语义单元切，不多拆 |

> `ik_max_word` 写出 "知识库" 和 "知识"、"库" 三个词条——用户搜"知识"时也能命中"知识库"这篇文档。召回率最高的代价是索引表更大。

### 4.5 完整的检索流水线

```
写入时（索引）：
  文档 → ik_max_word 切分 → 建立倒排索引表
  "杭州西湖半日游" → ["杭州", "西湖", "半日", "游", "杭州西湖", "半日游"]

搜索时（查询）：
  查询 → ik_smart 切分 → 查倒排索引 → 合并结果 → BM25 排序
  "西湖攻略" → ["西湖", "攻略"] → 命中 [doc1, doc3] → 按 BM25 打分排序
```

**检索的时候不会用 ik_max_word，因为切太细反而把无关文档也搜出来。**

## 五、BM25 算法

### 5.1 比 TF-IDF 强在哪

TF-IDF 是 BM25 的前身，核心缺陷有两个：

```
TF-IDF 的问题：
  问题 1：「的」出现 1000 次 = 1000 分，堆砌关键词就能刷排名
  问题 2：10 万字的书提了 3 次"跑步" = 100 字的笔记提了 3 次 = 同样分数

BM25 的改进：
  改进 1：词频到一定次数后分数不再增长（饱和）
  改进 2：文档越长，单位词频的权重越低（归一化）
```

**TF-IDF 是线性思维，BM25 是非线性思维。**

### 5.2 BM25 三个核心策略

| 策略 | 做什么 | 为什么 | 举个🌰 |
|------|--------|--------|--------|
| **词频饱和** | 词出现 10 次和 100 次，分数差别不大 | 防止关键词堆砌刷排名 | 一篇文提了 100 次「跑步」，不比其他提过 10 次的相关 10 倍 |
| **文档长度归一化** | 长文档"扣分"更多 | 公平对比短文档和长文档 | 100 字笔记里有 2 次「跑步」= 占比 2%；10 万字书里有 2 次 = 几乎忽略 |
| **稀有词权重高** | "IK分词" 比 "的" 更重要 | 区分信息含量 | 搜「BM25」只命中 1% 的文档 → 每一篇都很关键 |

```
TF-IDF：  词频 ∝ 评分（线性，刷词数就能刷排名）
BM25：    词频 √ 评分（非线性，趋近饱和，刷不动）
```

### 5.3 BM25 三个参数

| 参数 | 控制什么 | 默认值 |
|------|---------|--------|
| `k1` | 词频饱和度 | 1.2 |
| `b` | 文档长度影响 | 0.75 |
| `boost` | 字段权重 | 1.0 |

**不需要手动调。** ES 默认使用 BM25，大多数场景直接生效。

### 5.4 一句话记住 BM25

> **一个词在一篇文档中反复出现很重要，但不是线性重要——出现 100 次不等于相关 100 倍；**
> **一个词在越少的文档中出现也很重要，说明它很有区分度；**
> **长文档要扣分，因为讨论范围更广，某一特定词的相对重要性更低。**

你的直觉可以这样保底：**BM25 = 词频「减速」+ 文档长度「纠正」+ 稀有词「加钱」。**

### 5.5 IK + 倒排索引 + BM25：三者串起来

```
① 建索引 → ik_max_word 分词 → 倒排索引表（"杭州西湖"同时存 "杭州"、"西湖"、"杭州西湖"）
② 搜索   → ik_smart 分词 → 查表 → 召回文档列表
③ 排序   → BM25 对召回的文档打分排序 → 返回 Top K
```

**理解了这三者串起来的流水线，就理解了 ElasticSearch 的核心。**

## 六、基本操作

### 6.1 索引 CRUD

```js
// 创建索引
client.indices.create({
  index: 'travel_journal',
  mappings: {
    properties: {
      title: { type: 'text', analyzer: 'ik_max_word' },
      tags: { type: 'keyword' },          // keyword = 不分词，精确匹配
      mood: { type: 'keyword' },
      priority: { type: 'integer' },
      created_at: { type: 'date' }
    }
  }
});

// 查看所有索引
client.cat.indices({ format: 'json' });
```

### 6.2 文档 CRUD

```js
// 新增
client.index({ index: 'travel_journal', document: { title: '游记', ... } });

// 查询
client.get({ index: 'travel_journal', id: 'abc123' });

// 更新
client.update({ index: 'travel_journal', id: 'abc123', doc: { title: '新标题' } });

// 删除
client.delete({ index: 'travel_journal', id: 'abc123' });

// 搜索
client.search({ index: 'travel_journal', query: { match: { title: '西湖' } } });
```

### 6.3 MySQL vs ES 对照表

| MySQL | ES | 说明 |
|-------|----|------|
| Database | — | ES 没有 database 概念 |
| Table | Index（索引） | 类似表，但底层是倒排索引结构 |
| Row | Document（文档） | JSON 格式，每个文档一个 `_id` |
| Column | Field（字段） | 有 `text`/`keyword`/`integer`/`date` 等类型 |
| SQL | REST API | `GET /index/_search` |
| 模糊搜索 `LIKE` | `match` 查询 | ES 毫秒级，MySQL 全表扫 |

## 七、混合检索架构

```
用户查询
    │
    ▼
LLM 重写（extend 多角度问句）
    │
    ├──→ ES 关键词检索 ──→ hits_es
    │
    └──→ Milvus 语义检索 ──→ hits_milvus
              │
              ▼
         全量合并去重
              │
              ▼
           Rerank（重排序）
              │
              ▼
          LLM 作答
```

这就是 `examples/es-test/src/rag/hybrid-retrieval.mjs` 做的事——ES 和 Milvus 各取所长，统一路由给 LLM。

## 八、核心洞察

### 🔑 关键词和语义不是替代关系，是互补关系

```
Milvus 语义检索 → "杭州旅游攻略" 能命中 "西湖游玩指南"
ES 关键词检索   → "errorCode=5001" 绝对精确，不会漂到 "5002"
```

Agentic RAG 的价值不在于选其中一种，而在于**由 LLM 来判断"这个查询适合语义还是关键词"**，再分别走不同的检索通道。

### 🔑 ES 不是数据库，是搜索引擎

MySQL 存的是"业务原始数据"，ES 存的是"检索索引"。ES 的数据可以从 MySQL 同步过来（通过 Logstash 或自定义同步脚本），也可以丢了重建——它不替代 MySQL，而是补 MySQL 的检索短板。

### 踩坑：Docker 里跑 Attu 不能用 localhost 连 Milvus

Milvus 和 Attu 都跑在 Docker 容器内时，Attu 连接地址填 `localhost:19530` 会报错：

```
14 UNAVAILABLE: No connection established
```

**根因：** Attu 在容器里，`localhost` 指的是 Attu 自己的容器，不是宿主机。即使两者在同一个 Docker 网络下，也不能用 `localhost` 互通。

**修复：** 地址改成 Milvus 容器的 **container_name**：

```
# ❌ 错误
地址: localhost:19530

# ✅ 正确
地址: milvus-standalone:19530
```

Docker 会为同网络下的容器自动做 DNS 解析，容器名直接能当域名用。这和前面 Nest 连 MySQL 用 `host: "mysql-prod"` 的道理一样——容器之间的 `localhost` 各自独立，要用容器名互访。
