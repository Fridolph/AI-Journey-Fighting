# 后端分层、错误协议与注释约定

## 分层职责

```text
Controller：接收 HTTP 参数、绑定 Pipe、调用 Service
Service：业务编排、调用 Repository、组装 code/data/msg 等业务响应
Repository：执行 SQL 或 TypeORM 操作、返回数据或操作结果
全局异常过滤器：把异常转为 HTTP 状态码和统一错误响应
```

- Repository 不返回 `code`、`msg` 等接口响应字段；可返回实体、查询行、影响行数，或在目标不存在时抛出明确异常。
- 跨表写入必须保持同一事务管理器。当前创建 user、角色关联和 profile 的事务由创建仓库持有；以后若 Service 编排多个仓库写入，应共享同一个事务 manager，避免每个仓库各开事务。
- 单条 UPDATE 不额外开启事务。影响行数为零时需区分“目标不存在”与“重复提交原值”；本项目采用更新后按需复查存在性，不存在才抛 404。
- 查询列表默认第 1 页、每页 10 条，仅缺省值使用默认值，非法值不能静默兜底。单用户查询必须提供合法 ID，并固定只取一条。
- 角色 ID 用于关联，角色 code 用于业务规则；创建用户时按 `super_admin` 拒绝超管角色，不能依赖 ID 为 1。

## 错误协议

错误 HTTP 状态与响应 `code` 保持一致，示例：

```json
{
  "code": 400,
  "msg": "请求参数校验失败",
  "timestamp": "2026-11-09T00:00:00.000Z",
  "path": "/api/v1/users/18/profile",
  "errors": [{ "path": "nickname", "code": "invalid_type", "message": "昵称必须是字符串，不能为 null" }]
}
```

- `errors` 只用于公开的参数校验详情，仅保留 `path/code/message`，不返回原始输入。
- 重复键映射 409，外键关联冲突映射 409，关联目标不存在映射 400；未识别的数据库错误与内部错误使用通用 500 提示。
- 客户端不接收 SQL、数据库原始错误或堆栈；日志不记录请求体、完整 headers、SQL 参数，避免保存密码和令牌。4xx 使用 warn，5xx 使用 error。
- 前端错误归一化优先读取 `msg`，兼容已有 `message`，保留字段校验详情；HTTP 错误与 HTTP 200 中的业务失败均抛出 `ApiError`。

## 注释详略

- Controller：业务目的 + 必要的 `@param` / `@returns`，不复述路由和显而易见的转发过程，不重复罗列下层异常。
- Service：说明业务目的，按需补充参数、返回值和重要异常；只在存在关键业务决策时写 `@remarks`。
- Repository：详细说明事务范围、筛选规则、空值语义、唯一约束、存在性判断和查询返回结构，便于核对需求。
- Entity：每个字段、关系旁用简短行注释说明业务意义，尤其是枚举、空值、主外键、唯一性和级联方向。
- Module、普通 constructor、基础 TS 类型语法不写模板式注释；注释避免重复代码，行为变化时同步更新。

## 验收重点

1. 不存在的资料更新返回 404；原值重复提交返回成功，null 和 gender=0 不丢失。
2. 非法分页返回 400；缺省分页有效；缺少单用户 ID 不执行查询。
3. 任意 ID 对应的 `super_admin` 都不能在创建用户时分配；角色或资料写入失败不产生半成品用户。
4. 编辑请求、删除缓存都使用列表的 `userId`；错误提示展示归一化消息。
